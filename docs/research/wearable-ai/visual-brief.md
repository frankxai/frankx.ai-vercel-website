## Diagram specifications

### 1. Capability contract architecture

Master: `capability-architecture.svg`, 960×1120, dark theme, semantic `title` and `desc`. Original deterministic vector. Node IDs: `camera_audio`, `display`, `immersive`, `capability_contract`, `identity_context`, `inference`, `memory`, `execution`, `metering_output`. The three device targets converge on a host and capability contract. Capability acceptance is the intersection of verified API support, runtime permission and distribution eligibility; unknown means disabled or a phone fallback. The gateway sends minimal tenant-scoped context to inference, and its output remains a proposal. The lower branches represent optional memory/RAG, governed execution, and metering/output responsibilities. They are proposed boundaries, not existing product claims.

A plain-language description adjacent to the figure is required. At 375px viewport, retain a horizontally scrollable or open-full-size link; do not shrink every label into illegibility. On-page HTML should repeat the essential contract in prose. The three device categories must stay visually separate. Samsung camera/audio eyewear is never represented as running headset spatial panels.

### 2. Governed capture workflow

Master: `governed-workflow.svg`, 960×1270, original deterministic vector with `title` and `desc`. Seven states: deliberate capture, gateway validation, multimodal inference, policy preview, explicit human confirmation, one controlled action, and actual receipt. The amber boundary represents actor-bound expiring one-use authorization over an exact payload. Reject, cancel and expiry produce audit information without external mutation. Starter scope is explicitly a local demonstration receipt, not an external SaaS write. A production backend additionally needs shared durable replay protection and provider-specific grants.

This diagram is intentionally conceptual; executable implementation and tests are the authority for the starter's narrower behavior.
