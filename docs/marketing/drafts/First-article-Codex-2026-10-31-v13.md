# Fable 5.1, Opus 5.5 or GPT-6: choose the model around the work

Author: Codex · Created 2026-10-31 · Revision 13

Private manuscript. Not published, not a tested product claim. Source/editorial, independent and founder review pending.


You have a project to finish and several capable models available. The useful choice starts with the work: the decision you need, the sources it depends on and the output you intend to keep. A larger model may improve a difficult step. It can also make an already adequate step more expensive without changing the result you care about.

The public model names are real. Anthropic documents Claude Fable 5.1 and Opus 5.5. OpenAI documents GPT-6 Astra, GPT-6.1 Sol and GPT-6.1 Terra. Check availability in your actual product or account; a published API model is not proof that every subscription, integration or region exposes it.

## Choose a job with a finish

Use a task from your current work. For a coding comparison, select one issue in an existing repository with a clear acceptance condition. For research, choose a question whose answer can be checked against a small set of primary sources. For writing, specify the reader, useful decision, source material and editorial standard.

Keep the initial task and inputs the same. A polished response to an easier prompt does not answer whether a model improved the difficult job. Preserve the original output before editing it, then record the changes required to make it useful.

## Use the provider's guidance as a starting hypothesis

Anthropic's Fable documentation directs most workloads toward Opus 5.5 and reserves Fable 5.1 for demanding work where evaluation still shows a need. OpenAI describes Astra for its most demanding work, Sol as a lower-cost option for complex tasks, and Terra for visual reasoning, computer use and writing. These are provider descriptions. Your task still needs a comparison.

Start with the option you already have that can plausibly do the job. Increase effort or change the model when a specific failure remains. Record the model identifier, host, effort setting and date. The assistant application, connected tools and supplied context can change the result even when the model name stays the same.

## Count the work after the answer

Compare useful output, repairs and recovery. Did the research answer distinguish a source from an inference? Did the code preserve the required behavior? Can you edit the exported artifact? Can another session identify the accepted decision and next action?

Record setup time separately from active work and review. If you have actual usage records, retain their units and billing basis. A subscription allowance, an API price and a measured task cost describe different things. Avoid claiming a cheaper workflow from a token price alone.

## Keep a decision you can revisit

Write a short record: task, current choice, observed result, unresolved weakness and the condition that would make you switch. Use it when another model arrives. The next comparison can start from the same useful task instead of another round of general impressions.

For a founder building across projects, this record also gives an agent team a stable reference. Put the accepted decision beside the work and link to its source. Keep private business context out of a public comparison.

This article provides a selection method, not a completed model benchmark. No model was run against the example tasks for this manuscript. The next useful addition is one real task with its original outputs and corrections, reviewed at the exact published revision.
