# ADR-0003: Retrieval filters to the clause in force on the question's date

## Status

Accepted

## Context

A contract is not one document; it is an original plus its amendments, each changing some clauses
and leaving others alone. Semantic similarity has no opinion about which version is current — a
superseded termination clause and the one in force are near-identical text, and the superseded one
is often the better embedding match because the amendment is shorter and more specific.

This is the mechanism behind the failure in `01-discovery.md` § 11. Treating it as a prompt problem
("tell the model to prefer the latest") would put a probabilistic guard on a deterministic fact.

## Decision

Every clause carries `contract_id`, `amendment` and `effective_date` as typed metadata at ingest
(`services/ingest/src/split.py:L34`). Retrieval filters by effective date before ranking
(`services/qa/src/retrieve.py:L48`), so superseded clauses cannot be retrieved at all unless the
question names an earlier date. The rerank pass drops any clause whose contract has a later
amendment covering the same clause number.

## Consequences

Easier: "as of" questions work by construction (`golden-007`), and a whole class of wrong answer
becomes structurally impossible rather than discouraged.

Harder: ingest has to parse amendment structure correctly, and a document that fails to split
silently removes a contract from the corpus. That is why the re-index report names every failed
split and `02-user-flows.md` flow 2 has a failure branch for it.

Open risk: the filter is only as good as the metadata. A mis-tagged effective date produces a
confidently wrong answer with a valid-looking citation, and no eval case in the current suite would
catch it — the cases grade answers, not metadata. Named here, and named again in
`06-evals/rubric.md` § what this suite does not cover.

## Alternatives considered

| Alternative | Why not |
|---|---|
| Prompt the model to prefer the latest amendment | A probabilistic guard on a deterministic fact, and the failure mode is silent |
| Index only the current version of each clause | Kills as-of questions, which are a real need during disputes and renewals |
| Post-filter after ranking | The superseded clause consumes one of the eight retrieval slots, so recall drops for the reason the filter exists to prevent |

## Trust boundary

Clause metadata is T1 — the firm's own pipeline produced it — while clause text is T3. The filter
runs on T1 metadata, which is why it is trustworthy in a way the clause text is not. This
distinction is exactly the one `05-trust-boundary.md`'s open finding erases at the prompt: the
metadata is passed as typed fields and the text is not.
