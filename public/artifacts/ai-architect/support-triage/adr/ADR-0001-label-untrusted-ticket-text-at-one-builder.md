# ADR-0001: Label untrusted ticket text at one prompt builder

## Status

Accepted

## Context

The ticket body is written by a stranger and is the main input to classification and drafting.
Discovery found two consumers of that text (`apps/worker/src/triage.ts`,
`apps/worker/src/draft.ts`) and an existing prompt package. Either each consumer builds its own
prompt string, in which case the wrapper is a convention that decays, or one builder owns the
labelling and both consumers call it.

## Decision

All prompt construction goes through `packages/prompt/src/build.ts`. Ticket text is wrapped as
`<untrusted_ticket>` and macro text as `<approved_macro>`, both in the user message. The system
message is built separately at `packages/prompt/src/system.ts` and names both wrappers, stating
that their contents are data to classify, never instructions to follow. No consumer concatenates
retrieved or inbound text into the system message.

## Consequences

Easier: one place to change when a new label is needed, one place for an eval case to target, and
`injection-003` can test a forged closing tag against the real builder.

Harder: every new consumer has to import the package, and a consumer written in another language
would have to reimplement the labelling. If that happens, this ADR is superseded rather than
quietly bent.

Open risk: labelling constrains where text lands, not what the model does with it. A model can
still be persuaded by well-crafted data. The structural control is that the drafted reply is T3
and cannot be sent by the system at all.

## Alternatives considered

| Alternative | Why not |
|---|---|
| Wrapper applied at each call site | Two call sites today, more later; the convention decays silently and nothing fails loudly when it does |
| Strip instruction-shaped text from the body before prompting | Filtering an open text field is a losing game, and it destroys evidence the support agent needs to read |
| A separate classifier model with no free text at all | Loses the drafting half of the outcome, which is most of the benefit in `04-roi.md` |

## Trust boundary

The builder reads T3 (ticket, thread) and T1 (macros, queue definitions) and writes nothing. It
crosses no tier: it produces a prompt string that the worker sends. The worker holds T2 tool
credentials for the support platform, all read or internal-note scoped, and holds no send tool.
