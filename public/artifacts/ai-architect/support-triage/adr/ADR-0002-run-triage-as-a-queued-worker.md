# ADR-0002: Run triage as a queued worker, not inside the intake request

## Status

Accepted

## Context

The support platform's intake webhook is a request with a short patience. The triage job does a
classification call, up to three macro retrievals, a drafting call and up to three attempts on
failure. The longest run observed in the fixture is 41 seconds (`fx.run.longest`), against a
request-scoped ceiling of 300 seconds (`fx.run.ceiling`). Today's number fits; the shape of the
work is what does not — retries and a slow provider are ordinary, and a request that dies takes
the ticket's only processing attempt with it.

## Decision

The intake route enqueues the ticket id and returns. A worker consumes the queue and runs the
whole triage job. Retries live in the worker, bounded at three attempts in code. A job that
exhausts its attempts stays in the queue and the ticket stays untouched in the inbox.

## Consequences

Easier: provider slowness stops being a webhook timeout, retries are free to be slower than a
request, and the degraded state is exactly the manual process the team already knows.

Harder: two runtimes to deploy and one more place for a job to be stuck. Queue depth becomes the
signal that matters, and it is the system's only alert.

Open risk: nothing pages anyone. At depth 50 the support lead gets an email, and the team may not
read it out of hours. Accepted deliberately (`01-discovery.md` § 33) because the failure mode is
"support works the inbox by hand", not data loss.

## Alternatives considered

| Alternative | Why not |
|---|---|
| Run inside the intake request | The 41 s median run is fine until a provider is slow; then the ticket loses its only attempt and nobody knows |
| Durable workflow engine per ticket | Adds a runtime nobody on a five-person support team operates, for a job whose steps fit on one screen |
| Cron batch every 15 minutes | Turns first-reply latency into a fixed 15-minute floor, which is the number this system exists to lower |

## Trust boundary

The worker holds the T2 support-platform credentials: read ticket, write internal note, set route.
It does not hold send. The queue itself is T1 — it carries ticket ids, not ticket text, so a queue
dump does not leak customer content.

## Verification

```bash
rg -n "enqueue\(" apps/api/src/routes/intake.ts       # expect 1 hit, L22 — the route enqueues and returns
rg -n "attempts >= 3" apps/worker/src/triage.ts       # expect 1 hit, L64 — bounded retries in code
rg -n "send_email" apps/worker/src/tools.ts           # expect 0 hits — no send capability
```
