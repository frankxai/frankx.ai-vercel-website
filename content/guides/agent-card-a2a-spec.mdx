# The Agent Card

The [Agent2Agent (A2A) protocol](https://a2a-protocol.org/latest/specification/) defines a JSON document called an **Agent Card** that describes an AI agent's identity, supported interfaces, capabilities, security requirements, and skills. A public Card is discoverable at `/.well-known/agent-card.json` on the agent's domain.

This is the portability contract. Ship an Agent Card with your agent and:

- Compatible clients can discover the interfaces and skills you actually expose.
- An orchestrator can decide whether it supports one of your declared protocol bindings.
- You can change the implementation stack without changing the public Card when the advertised behavior and interfaces remain compatible.

This guide targets the current A2A 1.0 shape. Older examples with a top-level `url`, an `authentication` object, or a pre-1.0 discovery filename should not be copied into a new deployment.

This guide walks every field of the A2A Agent Card, with examples, gotchas, and production notes.

---

## Minimum valid Agent Card

```json
{
  "name": "First Agent — Research Assistant",
  "description": "A research assistant that answers questions with cited sources.",
  "supportedInterfaces": [
    {
      "url": "https://agent.example.com/a2a/v1",
      "protocolBinding": "HTTP+JSON",
      "protocolVersion": "1.0"
    }
  ],
  "provider": {
    "organization": "Frank Riemer",
    "url": "https://frankx.ai"
  },
  "version": "0.1.0",
  "capabilities": {
    "streaming": false,
    "pushNotifications": false
  },
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["text/plain", "application/json"],
  "skills": [
    {
      "id": "research-with-sources",
      "name": "Research with sources",
      "description": "Given a question, searches the web and returns a structured Research object.",
      "tags": ["research", "search"],
      "examples": ["What changed in the Vercel AI SDK v5 release?"],
      "inputModes": ["text/plain"],
      "outputModes": ["application/json"]
    }
  ]
}
```

This is a minimal public A2A 1.0 Agent Card with no declared authentication requirement. The required fields are present; optional production fields can be added as the service boundary becomes more sophisticated.

## Identity fields

### `name` (required)

Human-readable name. One line, no branding fluff.

**Good:** `"First Agent — Research Assistant"`, `"Acme Support Triage"`, `"Invoice OCR Agent"`
**Bad:** `"AI-Powered Next-Gen Research Platform™"`, `"agent-47"`

### `description` (required)

One paragraph, 100-400 characters. Describes what the agent does and — importantly — what it's for. Other agents and humans read this to decide whether to route work to you.

**Good:**
> "A research assistant that answers factual questions with 2-4 cited sources. Returns structured output with confidence level and short caveats. Best for: tech/product research, comparison questions, up-to-date facts. Not for: medical, legal, or financial advice."

**Bad:**
> "An AI agent that helps with things."

Be specific about **what it's for AND what it's not for.** Saving future callers from misrouted requests is an architectural courtesy.

### `supportedInterfaces` (required)

An ordered list of the endpoints and protocol bindings the agent supports. The first entry is the preferred interface.

```json
"supportedInterfaces": [
  {
    "url": "https://agents.acme.com/support-triage/a2a/v1",
    "protocolBinding": "HTTP+JSON",
    "protocolVersion": "1.0"
  }
]
```

The core binding identifiers are `JSONRPC`, `GRPC`, and `HTTP+JSON`. Use an absolute HTTPS URL in production and declare only interfaces your server actually implements.

### `provider` (recommended)

Who's behind this agent. `{ organization, url }`. Used for attribution, trust, and escalation paths.

```json
"provider": {
  "organization": "Acme Corp",
  "url": "https://acme.com"
}
```

### `version` (required)

A version string for the agent. Semantic versioning is a practical convention: increment it when advertised behavior, skills, or response contracts change.

### `documentationUrl` (optional)

Link to human-readable docs. Saves callers from having to guess how your agent works.

---

## Capability fields

### `capabilities.streaming` (bool)

Does your agent support the protocol's streaming operation on the declared interface? Set this to `true` only when the server implements it; otherwise omit it or use `false`.

### `capabilities.pushNotifications` (bool)

Can the agent push status updates to a callback URL during long-running tasks? Typically `false` for simple agents. Set to `true` if you expose a `taskId` and allow clients to register webhook callbacks.

### `capabilities.extendedAgentCard` (bool)

Can an authenticated caller retrieve a richer Agent Card through the protocol's extended-card operation? Leave this unset or `false` unless that operation is implemented and protected.

---

## Security fields

### `securitySchemes` and `securityRequirements`

These optional fields declare how callers authenticate. `securitySchemes` names and defines the available mechanisms; `securityRequirements` selects which named schemes are required for the agent or a specific skill.

For a header API key:

```json
"securitySchemes": {
  "apiKey": {
    "apiKeySecurityScheme": {
      "description": "Workspace-scoped API key",
      "location": "header",
      "name": "X-API-Key"
    }
  }
},
"securityRequirements": [
  {
    "schemes": {
      "apiKey": {
        "list": []
      }
    }
  }
]
```

The current schema also supports HTTP authentication, OAuth 2.0, OpenID Connect, and mutual TLS. A deliberately public agent can omit both fields, but that does not remove the need for rate limits, abuse controls, and bounded tool permissions.

---

## I/O fields

### `defaultInputModes` (array)

Default MIME types or content modes the agent accepts. Typical values:

- `"text/plain"` — plain text
- `"application/json"` — structured JSON input
- `"image/png"`, `"image/jpeg"` — multimodal
- `"audio/wav"` — for voice agents

### `defaultOutputModes` (array)

What the agent returns. Same value set as inputs. For a structured-output agent, typically `["text/plain", "application/json"]`.

---

## Skills — the most important field

A skill is a single capability the agent exposes. One agent, one or more skills. For a multi-capability agent, list each skill separately.

```json
"skills": [
  {
    "id": "research-with-sources",
    "name": "Research with sources",
    "description": "Given a question, searches the web, synthesizes an answer, returns cited Research object.",
    "tags": ["research", "search", "summarization"],
    "examples": [
      "What changed in the Vercel AI SDK v5 release?",
      "Compare Claude Sonnet 4.6 and GPT-5 for tool use."
    ],
    "inputModes": ["text/plain"],
    "outputModes": ["application/json"]
  }
]
```

### Per-skill fields

- `id` (required) — unique, stable identifier for this skill in the Card.
- `name` (required) — human-readable.
- `description` (required) — what this skill does and what it's for.
- `tags` (required) — an array of short strings for discovery. Think of these as categories an orchestrator can use to match skills to requests.
- `examples` (recommended) — 3-5 example inputs. Critical for other agents that want to decide if you're the right router target.
- `inputModes` / `outputModes` — override the agent-level defaults if this specific skill has different requirements.

### Skill IDs are a contract

Once you publish a skill with `id: "research-with-sources"`, keep it stable when the capability remains compatible. Catalogs and routing systems may retain that identifier even though A2A does not define skill IDs as direct invocation endpoints. If the contract changes materially, bump the agent version and document the migration.

## Publishing the Agent Card

Two baseline requirements:

1. **Serve the public Card at `/.well-known/agent-card.json`** on the agent's domain.
2. **Return JSON over HTTPS.** Use `Content-Type: application/json`. If browser-based clients on other origins must fetch this public Card, add an explicit CORS policy; server-to-server A2A clients do not rely on browser CORS.

For a deliberately public Card that browser clients may discover, a Next.js header rule can be:

```ts
// next.config.mjs
export default {
  async headers() {
    return [
      {
        source: '/.well-known/agent-card.json',
        headers: [
          { key: 'Content-Type', value: 'application/json' },
          { key: 'Access-Control-Allow-Origin', value: '*' },
        ],
      },
    ]
  },
}
```

And the file itself goes in `public/.well-known/agent-card.json`.

## Validation

Before shipping, validate your Card:

- **Authoritative:** validate with the [current A2A specification](https://a2a-protocol.org/latest/specification/) and an official A2A SDK for the protocol version declared in each interface.
- **Local shape guard:** a small `zod` schema can catch missing fields before the protocol-level validator runs:

```ts
import { z } from 'zod'

const AgentCardSchema = z.object({
  name: z.string(),
  description: z.string(),
  supportedInterfaces: z.array(z.object({
    url: z.string().url(),
    protocolBinding: z.enum(['JSONRPC', 'GRPC', 'HTTP+JSON']),
    protocolVersion: z.string(),
  })).min(1),
  provider: z
    .object({
      organization: z.string(),
      url: z.string().url(),
    })
    .optional(),
  version: z.string(),
  capabilities: z.object({
    streaming: z.boolean().optional(),
    pushNotifications: z.boolean().optional(),
    extendedAgentCard: z.boolean().optional(),
  }),
  securitySchemes: z.record(z.string(), z.unknown()).optional(),
  securityRequirements: z.array(z.unknown()).optional(),
  defaultInputModes: z.array(z.string()),
  defaultOutputModes: z.array(z.string()),
  skills: z.array(z.object({
    id: z.string(),
    name: z.string(),
    description: z.string(),
    tags: z.array(z.string()),
    examples: z.array(z.string()).optional(),
    inputModes: z.array(z.string()).optional(),
    outputModes: z.array(z.string()).optional(),
  })).min(1),
})

// parse your card
AgentCardSchema.parse(agentCardJson)
```

Passing this local guard proves only that the basic 1.0 shape is present. Protocol semantics, binding support, security requirements, and signatures still need validation against the declared A2A version.

## The Oracle Open Agent Specification connection

The Agent Card and [Oracle Open Agent Specification (Agent Spec)](https://oracle.github.io/agent-spec/) solve different portability problems. The Card is a public A2A discovery and interaction contract. Agent Spec is a framework-agnostic declarative language for describing executable agents and structured workflows.

Relationship:

- **Agent Card** = external interoperability contract. It names supported interfaces, security requirements, media types, capabilities, and skills.
- **Agent Spec** = portable implementation description. Compatible runtimes and adapters interpret its agent and flow components.

They can complement each other, but neither specification guarantees an automatic mapping to the other. If your platform generates a Card from an Agent Spec definition, test that mapping as release code and keep the public Card aligned with the endpoint that actually runs.

The [enterprise branch of the workshop (B6)](/workshops/build-first-ai-agent) covers OAS in depth. For your first agent, the Card alone is enough.

## Gotchas

### 1. Don't put secrets in the Card

The public Card must not contain API keys, internal URLs, customer IDs, or other secrets. `securitySchemes` describes authentication mechanisms; credentials are acquired and transmitted out of band.

### 2. Interface URLs must be reachable

If a public Card advertises `https://internal.corp.com/my-agent`, outside clients cannot use that interface. Keep each `supportedInterfaces[].url` aligned with the audience that can fetch the Card.

### 3. Skill IDs aren't display strings

`"id": "research-with-sources"` is a machine identifier — kebab-case, stable, meaningful. `"name": "Research with sources"` is what humans see. Don't conflate them.

### 4. `examples` are part of the contract

Callers use `examples` to decide if your skill is the right match for their intent. If you ship misleading examples, you get misrouted requests. Pick examples that are representative of the actual skill.

### 5. Browser discovery needs an explicit CORS decision

Server-to-server A2A clients are not governed by browser CORS. If a browser application on another origin must fetch a public Card, allow only the origins your use case requires—or use `*` only when the Card is intentionally public to every origin.

## Production checklist

Before exposing an Agent Card in production:

- [ ] All required fields populated (`name`, `description`, `supportedInterfaces`, `version`, `capabilities`, `defaultInputModes`, `defaultOutputModes`, `skills`)
- [ ] At least one skill with `id`, `name`, `description`, and `tags`; representative examples are strongly recommended
- [ ] Every declared interface URL is reachable by its intended audience and implements its declared binding/version
- [ ] Public Card served at `/.well-known/agent-card.json` with `Content-Type: application/json`
- [ ] Browser CORS policy added only if cross-origin browser discovery is intended
- [ ] Validated against the exact A2A version declared by each interface
- [ ] No secrets in the Card
- [ ] Security schemes and requirements match the server, or their omission is an intentional public-access decision with network-layer limits
- [ ] Version bumped if behavior changed since last publish
- [ ] Documentation URL points to real docs, not your company homepage
