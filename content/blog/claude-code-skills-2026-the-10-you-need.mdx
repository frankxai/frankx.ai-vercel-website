## What skills are

Skills are folders containing a `SKILL.md` file with YAML frontmatter (`name` and `description`) plus markdown operational rules and optional helper scripts. Claude preloads the short YAML description at startup and reads the full `SKILL.md` body when your prompt matches the task.

The `vercel-react-best-practices` skill contains 40+ rules about React inside Vercel — avoiding unnecessary `useEffect`, preferring Server Components, structuring data fetching. Claude reads those rules and applies them as constraints.

## Skills vs plugins vs commands vs subagents

| Primitive   | What It Is                                   | When It Activates                | Best For                                    |
| ----------- | -------------------------------------------- | -------------------------------- | ------------------------------------------- |
| **Skill**   | `SKILL.md` folder + optional `scripts/`      | Auto (description match)         | Domain standards, checklists, architecture  |
| **Plugin**  | Versioned bundle (`/plugin install`)         | Installed across repos / IDEs    | Sharing skills, hooks, commands, and MCP    |
| **Command** | Slash workflow (`.claude/commands/*.md`)     | On demand (`/command`)           | Deterministic operator tasks                |
| **Subagent**| Isolated context profile (`.claude/agents/`) | Delegated multi-step work        | Parallel research and independent verification |

Skills hold the reusable standards. Slash commands invoke repeatable workflows. Plugins distribute everything across VS Code, JetBrains, and CLI setups — see [Claude Code plugins vs skills](/guides/claude-code-plugins-vs-skills) and the interactive [Skills Hub](/skills).

## The 10 essential skills

### 1. vercel-react-best-practices

40+ rules for React in Vercel apps. Every component starts Server-first. Shifts to Client only when interaction requires it. Saves bundle weight across 170+ pages.

### 2. next-best-practices

App Router fundamentals. Layout nesting, route groups, parallel routes, metadata API. Correct route structure on the first try.

Update, November 2026: Vercel retired `next-best-practices` as a separate skill. On Next.js 16.3 and later, `next dev` writes the same guidance into the project's `AGENTS.md` and `CLAUDE.md` and ships it in the bundled docs, so there is nothing extra to install. The workflow skills that remain, such as `next-cache-components-optimizer`, now live in the [Next.js repository](https://github.com/vercel/next.js/tree/canary/skills).

### 3. shadcn-ui

shadcn/ui integration patterns. Extends through `cn()` and variant props. Keeps the design system coherent instead of fighting internal styles.

### 4. seo-content-writer

Content optimization for long-form writing. TL;DR-first structure, question-based H2s, FAQ inclusion, internal linking rules.

### 5. seo-fundamentals

Core SEO — crawlability, title tags, meta descriptions, canonicals, structured data. Caught 3 missing canonicals and 2 duplicate titles before I ran a crawl.

### 6. tailwind-css-patterns

Utility-first CSS conventions. Class grouping: layout → spacing → typography → color → state. Every component readable at a glance.

### 7. web-design-guidelines

Visual design for web. Spacing systems, typographic hierarchy, color contrast, visual weight. Shifts Claude from "technically correct" to "visually intentional."

### 8. architecture-patterns

System design for production apps. Separation of concerns, data flow, service boundaries. Kept the [ACOS](/acos) architecture clean as it grew.

### 9. clean-code

Code quality rules. Naming conventions, function length, abstraction levels. Every function name becomes a description of what it does. Code reviews are faster.

### 10. fixing-accessibility

WCAG 2.2 compliance. Semantic HTML, ARIA labels, keyboard navigation, focus management, color contrast. Passed WCAG 2.2 AA on first audit for the [prompt library](/prompt-library).

## How to add skills to Claude Code (global vs project templates)

You can install skills globally for personal habits across every repo, or commit project-scoped skills into `.claude/skills/` so your teammates and CI agents inherit the exact same guardrails:

```bash
# 1. Install proven open-source skill packs globally (~/.claude/skills/)
npx skills add vercel-labs/agent-skills -y -g             # vercel-react-best-practices, web-design-guidelines
npx skills add vercel/next.js -y -g                       # Next.js workflow skills (next-best-practices is now built into next dev)
npx skills add sickn33/antigravity-awesome-skills -y -g   # seo-content-writer, seo-fundamentals, architecture-patterns, clean-code
npx skills add ibelick/ui-skills -y -g                    # fixing-accessibility
npx skills add giuseppe-trisciuoglio/developer-kit -y -g  # shadcn-ui, tailwind-css-patterns
npx skills add frankxai/claude-skills-library -y -g       # optional: the FrankX packs

# 2. Verify active global skills
npx skills list -g
```

When setting up a reusable repository starter (`claude code templates`), separate universal instructions (`CLAUDE.md` / `AGENTS.md`) from on-demand domain skills so your startup token budget stays lean:

```text
your-repo/
├── CLAUDE.md                        # Always-on repo architecture, build commands & branch rules
├── AGENTS.md                        # Cross-agent mirror for Codex CLI, Cursor & OpenCode
└── .claude/
    ├── settings.json                # Scoped permissions & PreToolUse safety hooks
    ├── commands/                    # Explicit slash commands (/ship, /review)
    └── skills/                      # Auto-loaded only when task matches description
        └── api-contract-guard/
            ├── SKILL.md             # Rules + decision checklist (< 250 lines)
            └── scripts/
                └── check-openapi.mjs # Deterministic validator run by the agent
```

## Portable skill mapping across coding agents

If you switch between Claude Code, Codex CLI, Cursor, and Gemini/Antigravity, keep one canonical `SKILL.md` directory and project thin instruction pointers rather than maintaining four diverging prompt copies:

| Agent runtime | Always-on repo file | Skill discovery path | Tool & permission boundary |
| --- | --- | --- | --- |
| **Claude Code** | `CLAUDE.md` | `~/.claude/skills/<name>/SKILL.md` or `.claude/skills/` | `allowed-tools` frontmatter + `.claude/settings.json` hooks |
| **OpenAI Codex CLI** | `AGENTS.md` | `~/.codex/skills/<name>/SKILL.md` or `.agents/skills/` | `approval_policy` + sandbox mode in `~/.codex/config.toml` |
| **Cursor** | `AGENTS.md` / `.cursor/rules/*.mdc` | `.cursor/skills/<name>/SKILL.md`, `.agents/skills/`, or `~/.cursor/skills/` | IDE workspace approval + MCP server allowlist |
| **Antigravity / Gemini CLI** | `GEMINI.md` + `AGENTS.md` | `~/.gemini/config/skills/` (Antigravity) · `~/.gemini/skills/` (Gemini CLI) | Scoped tool declarations + workspace boundary rules |

## Building your own production skill (20 minutes)

Create `.claude/skills/brand-voice-check/SKILL.md` with explicit trigger boundaries in `description` and pair it with a runnable check script. For the deeper specification, read [Anatomy of a production skill](/guides/anatomy-of-a-production-skill).

```markdown
---
name: brand-voice-check
description: >-
  Use when drafting or reviewing public blog posts, product pages, or release
  notes. Checks concrete claims, sentence-case headings, and banned filler phrases.
---

# Brand voice and editorial check

## Rules

1. Lead with what the builder can make or verify in the next 10 minutes.
2. Pair architectural claims with an exact file path, command, or measured count.
3. Keep section headings and button labels in sentence case.
4. Run `node .claude/skills/brand-voice-check/scripts/audit-copy.mjs <file>` before opening a PR.
```

## Evaluating skills before global install

A prose skill earns a permanent slot in your setup only when you verify both trigger accuracy and fault detection. In [`frankxai/claude-skills-library`](https://github.com/frankxai/claude-skills-library), the public catalog checks every skill package's structure with `validate-spec`. That proves the package is well formed, not that the skill catches bugs: the catalog does not yet ship behavioral evals. Before promoting any skill into your global setup, test it against planted bugs with an executable check in `scripts/`:

| Verification check | Weak prompt-only skill | Production `SKILL.md` package |
| --- | --- | --- |
| **Startup token cost** | Dumps 2,000+ lines into `CLAUDE.md` on every turn | Loads ~40-token YAML `description`; reads body only on match |
| **Trigger precision** | Vague description (`"Helps with backend"`) fires randomly | Explicit `"Use when..."` scope tested against positive and negative prompts |
| **Fault detection** | Advises `"write accessible HTML"` in prose | Runs `axe-core` / AST script in `scripts/` and blocks broken output[^6] |
| **Portability** | Locked to one chat window | MIT-licensed folder portable across Claude Code, Codex, and CI |

Before adding any third-party skill globally:

1. **Test positive and negative triggers** — Confirm the YAML `description` fires on target tasks without hijacking unrelated prompts.
2. **Pair prose with deterministic scripts** — Put link checks, schema checks, and AST checks inside `scripts/` so Node or Python executes exact assertions[^5].
3. **Install from MIT sources you have read** — Browse the open catalog in [`frankxai/claude-skills-library`](https://github.com/frankxai/claude-skills-library) or generate your own `SKILL.md` in the [Skill Builder](/skills/builder).

## FAQ

### How many skills globally?

Start with 5-10. More adds context overhead. I run 12 globally, load more per project.

### Do skills work on Claude.ai?

Skills as filesystem files are Claude Code-specific. Claude.ai uses system prompts — same principles, different mechanism.

### Can skills conflict?

Yes. Two skills with opposing rules for the same situation create inconsistent behavior. Review for overlap before combining.

### How do I verify a skill loaded?

Ask Claude: "What skills are active?" It lists loaded context rules.

### Global vs project-level?

Global (`-g`): universal standards. Project-level: domain-specific rules. Use both.
