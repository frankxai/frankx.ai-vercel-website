This page is for engineers and AI architects who brief coding agents all day: Claude Code, Cursor, Codex. The short version: spoken briefs carry more context than typed ones because talking costs almost nothing, so structure them, keep exact identifiers on the keyboard, and read the transcript before you press enter. The full tool setup lives in the [Wispr Flow guide](/guides/wispr-flow); this post is the prompting method.

The smallest honest next move is one task. Pick the next agent brief you were going to type, dictate it with the template below instead, and compare what the agent does with it.

## What did I notice when I started dictating agent briefs?

I use Wispr Flow every day, and the place it changed my work most is the brief I hand to Claude Code agents.

One example. I dictated a single `/goal` brief that asked the agent to act as CEO, CMO and CTO for frankx.ai, audit every blog article, separate internal content from public content, and then work through a plan. Typed, that would have been three lines. Spoken, it came out long and layered: why the audit mattered, what "internal" meant on this site, which pages I was worried about, what a good outcome looked like.

That is the pattern I keep seeing. When I type, I compress, because every sentence costs effort. When I speak, I explain, because explaining is what speech is for. Agents do better with explanation. Most bad agent runs I see come from a brief that left out something the author knew and did not bother to write down.

## Why do spoken briefs carry more context?

Three reasons, all practical.

**Typing cost shapes what you include.** A typed prompt gets edited down to the essentials you can remember at the keyboard. Speaking removes that cost, so the background reasons, the edge cases and the "by the way, don't touch the pricing page" notes survive.

**Speech follows your reasoning order.** You naturally say why before what. That gives the agent the intent behind the task, which it needs when it hits a case your instructions did not cover.

**You hear the gaps.** Saying "and when it's done, it should..." out loud forces you to finish the sentence. Typed briefs often stop before the done criteria.

The cost is structure. A spoken ramble has the context and none of the order. The fix is a fixed shape you speak into.

## How should a spoken agent brief be structured?

Use six parts, in this order. Say the label out loud as you go; it gives the transcript headings and keeps you on track.

1. **Role.** Who the agent is for this task. "Act as a senior Next.js engineer reviewing this repo for SEO regressions."
2. **Goal.** The outcome in one or two sentences. What exists at the end that does not exist now.
3. **Context.** Why the task exists, what you already know, what you tried, what the reader or user cares about. This is the section voice improves most.
4. **Constraints.** What the agent must not do: files to leave alone, commands not to run, style rules, budget limits.
5. **Done criteria.** Observable conditions. "Every post in content/blog has a description between 120 and 160 characters."
6. **Verification.** How the agent proves it: which tests, which lint command, what to report back.

Here is the template I recommend. Copy it into a snippet so you can see it while you talk, or into your dictation tool's snippet library so a short trigger phrase inserts it.

```text
ROLE: Act as [role] for [project]. You are responsible for [scope].

GOAL: By the end of this session, [the concrete outcome].

CONTEXT: This matters because [reason]. What I already know: [facts].
What I tried: [attempts and results]. The person who will use this is
[audience], and they care about [their concern].

CONSTRAINTS: Do not [change, delete or run] [thing]. Keep [style rule].
Ask me before [risky action]. Stay inside [directories].

DONE WHEN: [observable condition 1]. [observable condition 2].
[observable condition 3].

VERIFY: Run [command]. Report [what to report]. List anything you
could not finish and why.

EXACT VALUES (type these by hand):
- Paths:
- Identifiers:
- Commands:
```

The last block matters. Speak everything above it, then type the exact values underneath.

## What should stay on the keyboard?

Dictation is very good at English and unreliable at strings that only mean something character by character. Type these:

- **File paths.** `app/blog/[slug]/page.tsx` spoken aloud comes back in creative forms.
- **Identifiers.** Function names, component names, environment variable names, database columns.
- **Regex and glob patterns.** One wrong character changes the match.
- **Shell commands and flags.** Especially anything destructive.
- **Exact numbers.** Version numbers, ports, limits, prices, line numbers.

A useful habit: speak the description, type the reference. "Update the hero component so the headline wraps on mobile," then paste `components/home/Hero.tsx` on the next line.

## How do I teach the dictation tool my repo vocabulary?

Wispr Flow has a personal dictionary that learns names and jargon, and you can add entries yourself. Spend five minutes adding the words you say most often that a general model would mangle:

- Repo and package names (`frankx.ai-vercel-website`, internal package names).
- Tool names: Claude Code, Codex, Cursor, MCP, Vercel, Supabase, pnpm.
- Product and component names you use in briefs.
- Teammate names you reference in context.

Then dictate a test paragraph that uses all of them and fix anything that came out wrong. Repeat after a week; the dictionary keeps learning from your corrections.

## How do I turn a spoken ramble into a clean brief?

Sometimes you will talk for two minutes and the result is all context with no order. Wispr Flow's Command Mode transforms selected text by voice. Select the ramble and say something like: "Restructure this into role, goal, context, constraints, done criteria and verification. Keep every fact. Do not add anything I did not say."

That last sentence is the important one. Any rewrite step can introduce assumptions, so read the restructured version against what you meant. You can do the same restructuring in the agent itself ("before you start, restate this brief in six sections and wait for my confirmation"), which has the advantage that you see the agent's understanding before it acts.

## Should I review the transcript before sending?

Always. Dictation cleanup is good, and it still makes mistakes, and an agent will act on whatever it receives. A misheard "don't" is the expensive one.

A quick review pass, under a minute:

1. Read the constraints section first. Check every negative survived.
2. Check names and numbers against the typed block.
3. Check the done criteria are observable. "Make it better" is not a done criterion.
4. Delete anything you said while thinking that you do not want the agent to act on.

## What protocol should I run this week?

Five working days, one change per day.

1. **Day 1: setup.** Install a dictation tool, turn on the training opt-out, and add ten repo and tool names to the dictionary.
2. **Day 2: one brief.** Dictate one real agent brief using the template. Type the exact-values block. Review, then send.
3. **Day 3: compare.** Take a task similar to one you briefed by typing last week. Dictate it. Compare how many clarifying questions the agent asked and how many corrections you made.
4. **Day 4: restructure.** Ramble a brief with no structure, then use Command Mode or the agent to restructure it. Check nothing was invented.
5. **Day 5: decide.** Keep voice for the briefs where it produced better runs. Keep typing for the rest.

Track two numbers per brief: the agent's clarifying questions and your corrections after the first pass. Those tell you more than any speed figure. If you want to measure the speed side too, the [speaking vs typing speed post](/blog/speaking-vs-typing-speed) has a five-minute self-test.

## Where does voice fit alongside Cursor, Codex and Claude Code?

Dictation sits outside the agent, so it works the same in all three: a terminal, an editor chat panel, a web prompt box. The method above does not depend on the agent. What changes is how much context each one can use. Agents that read the repo themselves benefit most from the "context" and "done criteria" sections, because the code supplies the facts and your voice supplies the intent.
