Your agent stack should follow the work you need finished.

**The short answer:** use a managed workspace for work your team reviews, a runtime for work your product executes, and a workflow engine for repeatable integrations. Start with one recurring job, one execution owner and a cost ceiling. Compare accepted outcomes, review time and recovery before adding another subscription.

The useful question is what you want to stop operating. A browser? A server? A task queue? An entire internal workflow? Vendors use “managed” for different boundaries, and each boundary leaves a different amount of work with you.

This guide separates those decisions. It covers internal production, such as research, content and operations, alongside external production, where a customer depends on your agent. Vendor facts and prices were checked on **September 7, 2026**. Recommendations are architectural judgments from documentation, not results from a performance benchmark.

## Choose the job before the agent

Consider a weekly customer research brief. A founder can request it in a workspace, inspect the sources and circulate it. That is already a useful production workflow.

Now sell that brief to 500 customers. You need customer identity, scoped data access, job status, retries, billing, support and a way to recover interrupted work. The research prompt may remain similar. The product around it changes substantially.

| Your immediate job | Start here | Why this layer fits | Evidence before expanding |
| --- | --- | --- | --- |
| Research, presentations and founder decisions | Your existing Claude or ChatGPT workspace; compare Hyperagent when sharing recurring agents matters | A person can direct the work and review the artifact | Source accuracy and reviewer minutes |
| Repeatable CRM, inbox and document routing | n8n, with a bounded model call where judgment is needed | Most steps already have known inputs and outputs | Correct routing and safe replay |
| A customer buys an asynchronous research or document job | Claude Managed Agents or an OpenAI application stack | Your product needs an execution API and durable job records | Tenant isolation, recovery and cost per accepted job |
| A persistent personal assistant across channels | OpenClaw or Hermes, with a host you can operate | You want control over the runtime, tools and memory | Backup restoration and permission boundaries |
| Software changes in a repository | A coding agent inside the existing branch, test and review process | A diff is a reviewable delivery artifact | Tests, preview behavior and maintainability |

Start with the software and subscriptions you already understand. A new tool earns its place when it removes a specific operating burden or passes a task evaluation that the current tool fails.

The table is a fit assessment. It does not establish that one model reasons better, that one agent finishes more tasks, or that a managed host covers every operating responsibility. The linked documentation in the following sections defines the vendor boundaries.

## Claude Managed Agents versus OpenAI

### Claude: buy more of the execution loop

[Claude Managed Agents](https://platform.claude.com/docs/en/managed-agents/overview) combines an agent definition, execution environment, session and event stream. The service manages the loop and context handling for asynchronous work. Environments can use Anthropic-hosted or self-hosted sandboxes. Sessions retain conversation and filesystem state; scheduling and steering are supported.

That makes it a sensible candidate when a document or research job already fits Claude and your team wants to operate less runtime machinery. Your application still decides whose files the session can see and what constitutes successful delivery.

The service is in beta. Anthropic states that Managed Agents is currently ineligible for Zero Data Retention and HIPAA BAA coverage. Those are concrete constraints for a buyer with such requirements, rather than a reason to exclude every ordinary founder workflow. Check the [current service documentation](https://platform.claude.com/docs/en/managed-agents/overview) against your data needs.

### OpenAI: separate the application from its compute

OpenAI's product-building alternative is the [Responses API](https://developers.openai.com/api/docs/guides/migrate-to-responses) and [Agents SDK](https://developers.openai.com/api/docs/guides/agents), with [background mode](https://developers.openai.com/api/docs/guides/background) for asynchronous responses. These are building blocks, so compare the assembled application with Claude's managed service.

[Sandbox agents](https://developers.openai.com/api/docs/guides/agents/sandboxes), currently beta, add files, commands, packages and resumable workspace state in the TypeScript and Python SDKs. The control loop can stay in your trusted application while execution runs in a separate sandbox. This is useful when you want provider choice and explicit control over auth, review and recovery outside the working container.

A background model response alone does not replace your customer job queue or guarantee that a business action happens once. Keep a durable job record and make external writes idempotent, so repeating a request does not create a second invoice or send the same delivery twice.

**Do not start a new implementation on Agent Builder.** OpenAI lists it as deprecated, with shutdown scheduled for November 30, 2026. ChatKit remains available. Follow the [current migration guidance](https://developers.openai.com/api/docs/guides/agent-builder).

| Decision | Claude Managed Agents | OpenAI application stack |
| --- | --- | --- |
| Want the vendor to operate more of the agent loop? | Strong reason to pilot | Expect to assemble and operate more application logic |
| Want explicit control over loop and compute boundaries? | Inspect supported environment and tool contracts | Strong reason to pilot SDK sandbox separation |
| Already have a trusted application backend? | Integrate sessions as workers | Reuse it for control, identity and recovery |
| Need a winner on output quality? | Evaluate on your tasks | Evaluate on the same tasks |

For human-operated work, compare [ChatGPT Work](https://learn.chatgpt.com/docs/get-started-with-work) separately from API infrastructure. Keep the coding-agent decision separate too: [Claude Code architecture](/blog/graph-engineering-claude-code) and [Codex architecture](/blog/graph-engineering-openai-codex) concern repository work and its review process.

### Workspace Agents: an internal automation alternative

OpenAI also offers [Workspace Agents](https://developers.openai.com/workspace-agents). Your systems can trigger a published ChatGPT workspace agent, so a scheduled business process can start work without a person opening a chat.

The [trigger API](https://developers.openai.com/workspace-agents/trigger-runs) durably queues an event, supports an idempotency key and returns a conversation link. Run-status polling is beta. **The agent's response cannot currently be retrieved through this API.** That makes the delivery path a central pilot question: can your team inspect and use the resulting work where it lands?

Access uses [workspace-scoped tokens](https://developers.openai.com/workspace-agents/authentication) and requires the relevant admin permissions. This is a useful shortlist candidate against Hyperagent for internal automation. For a product that must receive a structured customer result over an API, evaluate the Responses application stack directly.

## Hyperagent: pay for the shared workspace

[Hyperagent](https://www.hyperagent.com/docs/concepts/agents) is relevant when the team needs recurring agents, shared context and a place to inspect work. Its current monthly plans return the subscription price as credits, with larger plans adding a bonus. A $20 plan carries $20 in credits; $50 carries $55; $100 carries $115. Unused plan credits expire at the billing-period boundary. Runs pause on exhaustion unless you buy more credit or enable recharge. [Plan details](https://www.hyperagent.com/docs/billing/plans).

There is also a supported ChatGPT connection through OAuth: eligible GPT usage can draw on that subscription, while other models, tools and media still consume Hyperagent credits. This is a specific integration, not evidence that every ChatGPT subscription includes general API credits. See [Hyperagent's billing rules](https://www.hyperagent.com/docs/billing/plans).

Pilot one recurring deliverable. Ask a second person to find its instructions, inspect its evidence and take over when it fails. If that handoff is easier than in your current workspace, you have a concrete reason to pay for the product. A polished interface alone cannot establish the quality of the underlying work.

## n8n: keep predictable work predictable

[n8n Cloud](https://n8n.io/pricing/) starts at €20 per month billed annually for 2,500 executions. Pro starts at €50 per month billed annually for 10,000. The unit is a workflow execution, regardless of how many steps it contains. Third-party model usage belongs in a separate budget; n8n's AI assistant credits are not a general model-API allowance.

Use n8n when most of the path is known: receive a form, normalize fields, look up a record, classify the request, route an exception, update a system. Give the model the uncertain step and validate its output before the workflow continues.

For example, the model can propose a lead category with evidence. A rule then checks the allowed categories and required fields. The workflow records the decision and writes to the CRM. You can inspect the uncertain part without asking an agent to improvise every API interaction.

Self-hosting changes the operating burden. Also review the [n8n license](https://docs.n8n.io/sustainable-use-license/) before embedding or reselling it in a customer product; internal automation and commercial distribution are different use cases. The [n8n workflow guide](/blog/ultimate-n8n-workflow-2026) goes deeper into implementation.

## OpenClaw 2.0 or Hermes on Railway?

Separate the agent from the host. [OpenClaw 2.0](https://openclaw.ai/blog/openclaw-2-accidentally) develops the persistent assistant model across onboarding, tools, channels and personal context. [Hermes Agent](https://hermes-agent.nousresearch.com/docs/) is another portable runtime built around persistent memory and reusable skills. Both deserve a task-specific pilot if controlling the assistant environment matters to you.

| Question | OpenClaw | Hermes | Hosting consequence |
| --- | --- | --- | --- |
| What attracts a founder? | A persistent assistant and expanding channel ecosystem | A personal agent with memory and reusable skills | Choose by the workflow you can demonstrate |
| Where does the state live? | In the configured runtime and storage | In the configured runtime and storage | Identify the actual persistent paths before deploying |
| Who maintains it? | You or your chosen operator | You or your chosen operator | A template installation does not define a service contract |
| What should the pilot prove? | Channel permissions, restart recovery and useful recurring work | Skill reuse, memory boundaries and restart recovery | Restore from backup on a fresh instance |

[Railway](https://railway.com/pricing) manages infrastructure. It does not automatically become the operator of your agent's prompts, connected accounts, tools or memory. “Managed OpenClaw” is only meaningful once the host states who handles updates, backups, security incidents and support.

My starting recommendation is **one persistent assistant runtime**. Deploying OpenClaw and Hermes together means two memories, two update paths and two places to investigate a failure. Add the second only when a measured workflow justifies it. The [Hermes architecture guide](/blog/graph-engineering-hermes-agent) is a useful next step.

The platform-map mascot is OpenClaw's official lobster mark. Hermes uses its official documentation icon. The small studio companion in this article's hero is original editorial artwork, not a vendor mascot. Familiar characters make tools recognizable; they do not demonstrate reliability.

## The full cost: platform, tokens, execution and your time

Compare like billing units first. The following table is a dated price snapshot, not a forecast or a package recommendation. USD and EUR remain separate; taxes, negotiated discounts and exchange rates are excluded.

| Item | Published price or basis | What to add or watch |
| --- | --- | --- |
| Claude managed session | $0.08 per running session-hour | Model and applicable tools; idle time is not running time |
| OpenAI hosted container | From $0.03 per 20-minute 1 GB container session | Model and tools; eligible sessions have minute billing with a five-minute minimum |
| Hyperagent | $20, $50 or $100 monthly plans carry $20, $55 or $115 credits | Credit consumption, expiration, optional recharge and connection coverage |
| n8n Starter / Pro | €20 / €50 monthly equivalent, billed annually | Execution allowance and third-party API usage |
| Railway Hobby / Pro | $5 / $20 monthly minimum, including that amount of usage | Resources above the minimum, egress and external APIs |

Sources: [Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing), [OpenAI pricing](https://developers.openai.com/api/docs/pricing), [Hyperagent plans](https://www.hyperagent.com/docs/billing/plans), [n8n pricing](https://n8n.io/pricing/) and [Railway pricing](https://railway.com/pricing).

### Model costs at a stated token volume

Here is one priced-token illustration: **50,000 uncached input tokens and 10,000 output tokens**, counted across the entire job. Standard short-context rates; no cache, batch, fast-mode, regional or long-context adjustments. The tokenizers differ, so equal token counts do not imply equal text or quality.

| Model | Input / million tokens | Output / million tokens | Model-only illustration |
| --- | ---: | ---: | ---: |
| Claude Sonnet 5 | $2 | $10 | $0.20 |
| Claude Opus 5 | $5 | $25 | $0.50 |
| GPT-5.6 Sol | $2 | $10 | $0.20 |
| GPT-5.6 Terra | $1 | $6 | $0.11 |
| GPT-5.6 Luna | $0.10 | $0.60 | $0.011 |
| GPT-6 Astra | $5 | $25 | $0.50 |

These are [Anthropic's](https://platform.claude.com/docs/en/about-claude/pricing) and [OpenAI's](https://developers.openai.com/api/docs/pricing) published rates on the review date. Sonnet 5's $2/$10 rate is now standard; the previously announced September increase was canceled. OpenAI describes Sol pricing as promotional, available at least through November 21, 2026. Recheck both before setting a customer price.

A model-only number excludes retrieved context, repeated tool turns, retries and review. If your measured job uses 300,000 input tokens, put 300,000 in the calculation. A large context window is capacity, not a promise that every job should fill it.

### A transparent Railway estimate

Assume an always-on assistant consumes an average of 1 GB RAM and 0.5 vCPU, with a 5 GB volume, for 30 days. Railway's published per-second rates give approximately **$20.79 in resource usage**, before egress. On a plan with a $20 included-usage minimum, the calculation is approximately $20.79, rather than $20 plus $20.79. Model and tool bills remain separate. [Railway resource pricing](https://railway.com/pricing).

This is a capacity assumption, not an observed Hermes or OpenClaw bill. Doubling the assumed memory and CPU to 2 GB and 1 vCPU, while keeping the same volume, gives approximately $40.80. Measure memory and CPU consumption during the pilot; browser activity can change the profile.

### Price an accepted outcome

<Diagram src="/images/blog/managed-ai-agents/outcome-economics.svg" alt="Illustrative monthly economics: 1,000 jobs cost 200 dollars in model usage, 40 dollars in managed runtime, 50 dollars in other infrastructure and 2,000 dollars in review time. Total 2,290 dollars divided by 900 accepted outcomes is 2.54 dollars each. These are assumptions, not benchmark results." width={1200} height={840} scrollable caption="An authored planning example. Human review is an economic cost here, even when it does not create a new cash invoice. Replace every assumption with pilot measurements." />

For this example, assume 1,000 jobs at $0.20 in model usage each, 30 running minutes per job at $0.08 an hour, $50 in other infrastructure, and two minutes of review per job valued at $60 an hour. Assume 900 outcomes are accepted. Tool fees, extra retries and incident labor are zero in this deliberately bounded example; add them when present.

The cash-like technical subtotal is $290. Review adds $2,000 of economic cost. Total cost is $2,290, or **$2.54 per accepted outcome** after rounding. The technical subtotal alone is about $0.32 per accepted outcome. Which number belongs in your decision depends on whether you are evaluating cash runway, capacity or gross margin.

The general equation is:

```text
Cost per accepted outcome =
  (platform + model + tools + compute + storage
   + review + operations + recovery)
  / accepted outcomes
```

Keep allocated engineering and operator labor consistent across candidates. Include unsuccessful attempts in the numerator. Count only deliverables that meet the same acceptance rule in the denominator. This is the reasoning behind [cost per verified outcome](/blog/cost-per-verified-outcome-infrastructure-roi).

### Costs a token table leaves out

| Cost | How it appears | What to measure |
| --- | --- | --- |
| Browsing and data | Search calls, browser sessions, paid datasets and proxies | Calls and minutes per accepted job |
| Context growth | Retrieved text, repeated history, memory and tool responses | Actual input, output and cache usage |
| Durable execution | Queue operations, retries, compute and retained state | Active time, restart count and retention |
| Integration work | OAuth maintenance, schema changes and broken connectors | Engineering hours per month |
| Human review | Checking citations, repairing outputs and handling exceptions | Minutes for accepted and rejected work |
| Operational incidents | Duplicate actions, failed deliveries and customer support | Recovery labor and affected jobs |
| Switching | Export, evaluation migration and replacement integrations | Time to move a representative workflow |

## An architecture for internal and external production

<Diagram src="/images/blog/managed-ai-agents/production-contract.svg" alt="A versioned job contract enters one durable execution owner, which invokes a bounded agent worker. The worker produces a draft and evidence for a policy or human review. Rejected work returns for bounded revision. Approved work goes to an idempotent executor and delivery receipt. Each transition updates a durable job record." width={1200} height={1120} scrollable caption="A reference pattern, not a vendor feature claim. One owner controls job state; the worker proposes outputs; validated actions produce a receipt." />

An internal workflow can start with a lightweight version of this pattern: a task brief, an agent workspace, a review and a saved artifact. An external product needs explicit identity and isolation throughout it.

| Boundary | Internal production | External customer production |
| --- | --- | --- |
| Identity | Named operator and workspace access | Customer, tenant and job authorization |
| Data | Approved source folders and connectors | Tenant-scoped retrieval, storage and credentials |
| Actions | Draft-first publishing and explicit send approval | Server-enforced policy and idempotent writes |
| Recovery | Visible failure and an owner who can rerun | Durable status, bounded retry and support path |
| Evidence | Sources, artifact and review note | Trace, acceptance result and delivery receipt |

For a FrankX-style content workflow, GitHub holds the versioned article, source ledger and assets. A branch produces a Vercel preview. A human reviews the actual page before a production merge. Notion can hold the research brief and editorial queue, with links back to the canonical source. That division gives each artifact a clear home.

For a customer research product, keep the durable job record in the application. A runtime worker returns a draft plus citations. A separate validation step checks required fields and evidence. Approval authorizes delivery. A timeout returns the job to a recoverable state instead of disappearing into a chat transcript.

## A 30-day founder rollout

Make the first pilot small enough that you can inspect every failure.

| Period | Work | Artifact | Decision |
| --- | --- | --- | --- |
| Days 1–3 | Pick one recurring job and define acceptance | 25 representative tasks, including awkward inputs | Is the job frequent and valuable enough? |
| Days 4–10 | Run two candidates on the same tasks, twice | Cost, output, evidence, review time and failure log | Which candidate reduces total work? |
| Days 11–20 | Connect the better candidate to a narrow real workflow | Draft deliveries with a fixed budget and tool boundary | Can another person operate it? |
| Days 21–30 | Test interruption, replay and restoration | Recovery receipt and updated unit economics | Expand, revise or stop |

Record the model version, agent instructions, available tools and input dataset. Review outputs against the same rubric, ideally without the reviewer seeing which candidate produced them. Fifty runs per candidate can reveal practical failure modes, but they do not establish broad statistical superiority.

Choose the acceptance rule before reviewing results. For a research brief, it could require a source for each material claim, working source links, no unsupported financial figures and a clear answer to the requested decision. A support triage workflow needs a different rubric.

Then stage the investment:

| Founder situation | First commitment | Expansion trigger |
| --- | --- | --- |
| Solo, learning the workflow | Existing workspace and manual review | Repetition consumes enough time to justify integration |
| Small team, shared recurring work | One managed workspace or n8n process | Another operator can maintain it and quality remains acceptable |
| Customer-facing agent product | One runtime, durable job state and scoped tools | Paid demand plus demonstrated recovery and viable unit economics |
| Enterprise delivery | Existing cloud and identity boundary | Security, procurement and operating requirements are satisfied |

I would start with the workflow already closest to revenue or a recurring founder bottleneck. Keep the acceptance record in view. It tells you whether the next investment should be a stronger model, a better source, a simpler process or less review time.

## Frequently Asked Questions

### What is OpenAI's closest alternative to Claude Managed Agents?

For a customer application, start with Responses and the Agents SDK, then add background execution and sandbox capabilities when the job needs them. For internal work, compare ChatGPT Work and Workspace Agents separately. Agent Builder is deprecated; its [published shutdown date](https://developers.openai.com/api/docs/guides/agent-builder) is November 30, 2026.

### Is Hyperagent better than Claude Managed Agents?

Hyperagent can be the better fit when your team wants a ready workspace for recurring agents. Claude Managed Agents can be the better fit when developers need an execution service behind a product. Choose the operating boundary first, then evaluate output quality on your own tasks.

### Does deploying Hermes on Railway make it fully managed?

It gives you managed hosting. Unless another operator explicitly provides the rest, you still maintain the agent's configuration, persistent data, connected accounts and upgrades. Budget for model usage, tools and operator time alongside the [Railway bill](https://railway.com/pricing).

### Does n8n include the model bill?

Treat third-party model API usage separately from workflow execution pricing. Read your [n8n plan](https://n8n.io/pricing/) and provider invoices together, particularly when loops or retries cause several model calls inside one workflow.

### What metric should decide the purchase?

Cost per accepted outcome, supported by acceptance rate, reviewer minutes, completion time and recovery behavior. Keep cash spending and allocated labor visible separately. A founder can then see whether a tool saves money, returns time or improves the delivered work.
